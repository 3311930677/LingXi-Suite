# 灵犀作为 OwO owopkg 插件的可行性评估

- 日期：2026-08-03
- 状态：技术评估（不含实现）
- 结论摘要：灵犀**整体不能**打包为 OwO `.owopkg` 插件；灵犀所需的 7 项核心能力全部触碰 OwO 插件 v1 的硬性安全红线。可行的落地形态是「灵犀保持独立程序 + 抽取一个纯本地确定性能力做成合规插件」，或「两项目平级 IPC 协作」。

---

## 1. 背景

两个大创项目：

- **OwO**：从零实现的 Windows 11 系统级输入法（C++20 / TSF / COM），当前处于 P3C（插件框架基础）。
- **灵犀（cross-app-assistant）**：Rust / Tauri 桌面输入辅助与桌面 Agent 原型，已实现拼音输入、AI 文本处理、QQ 回复草稿、桌宠。

诉求：把灵犀做成 OwO 的 `.owopkg` 插件，实现两项目融合。

本文基于 OwO 仓库 `docs/architecture/p3-kickoff.md`、`p3c-kickoff.md`、`p3c-acceptance.md` 与 `docs/risks.md` 的真实设计约束，评估该诉求的可行性。

---

## 2. OwO 插件框架（P3C）的硬约束

OwO 的插件沙箱是一个**极严格的安全模型**，v1 关键约束如下：

| 维度 | v1 规定 |
|---|---|
| 运行形态 | 仅 `runtime=process`、`api_version=1`、入口为安全的 `bin/*.exe` 相对路径 |
| 网络 | `network=true` **无条件拒绝**；AppContainer **无网络能力**（测试验证父进程可达的回环端口对子进程不可达） |
| 隔离 | 每插件独立**零能力 AppContainer** 进程；插件代码不进入 TSF / Core Service |
| 内存 | Job Object 单进程内存上限 **128 MiB** |
| 进程/并发 | 单插件最多 **1 个活动进程**、**1 个在途调用**，竞争调用立即返回忙碌 |
| 时长 | 单次调用总期限最大 **30 秒**；取消不合作或硬超时直接终止整个 Job |
| 包体 | `.owopkg` 最大 64 MiB，单文件解压后 64 MiB，总解压 256 MiB，最多 1024 项 |
| 签名 | 必须受信 CMS 签名（SHA-256、代码签名 EKU、强签名链）；**未签名一律拒绝**，无未签名开发模式 |
| 文件权限 | 安装树只读执行、数据树可写但无 `WRITE_DAC/WRITE_OWNER`；拒绝重解析点 |
| 调用入口 | P3C **不开放**可伪造的 `trusted_user_action` IPC/CLI/UI；真实 UI/快捷键入口留到 P4/P5 |

OwO 团队自己规划的 **P4 首个官方插件是「字符编码转换插件」**：无网络、低权限、纯计算、可完全本地测试。这明确界定了 owopkg 插件的适用边界。

---

## 3. 能力冲突矩阵

灵犀是「高权限桌面 Agent」，其核心能力与 OwO 插件的「零权限、无网络、有界计算沙箱」哲学完全相反。

| 灵犀依赖能力 | OwO 插件 v1 | 冲突说明 |
|---|---|---|
| 调云端 LLM API（DeepSeek / Qwen / OpenAI） | ❌ 禁止 | `network=true` 无条件拒绝；AppContainer 无网络 |
| 本地跑 Qwen2.5 1.5B（下载权重、大内存） | ❌ 禁止 | 内存上限 128 MiB；无网络下不了权重；包体上限 64 MiB |
| UIA 读写其他应用（QQ / 记事本 / 浏览器） | ❌ 不可能 | 零能力 AppContainer，无法访问其他进程 / 桌面 |
| 全局热键（Ctrl+Alt+Space 等） | ❌ 不可能 | 沙箱进程拿不到全局输入 |
| 剪贴板 / Ctrl+V 写回 | ❌ 不可能 | 无桌面交互能力 |
| Tauri 桌宠置顶窗 | ❌ 不可能 | 插件仅为 `bin/*.exe`，P3C 无 UI 入口 |
| 长驻后台监控 QQ 消息 | ❌ 不可能 | 单进程、单在途调用、30 秒期限，超时即杀 |

**7 项核心能力，7 项全部被禁**。因此灵犀无法整体沙箱化为 owopkg 插件，这是架构级冲突，非工程量问题。

---

## 4. 候选路线

### 方案 A：灵犀保持独立程序，抽一小块做合规插件（推荐）

- 灵犀主体（daemon + 桌宠 + AI + UIA）保持现状的 Rust / Tauri 独立程序不变。
- 从灵犀抽取一个**纯本地、无网络、确定性**的能力封装为真正的 `.owopkg`。候选：文本规整 / 编码转换 / 格式化（正好与 OwO P4 的字符编码转换方向一致）。
- 价值：两个项目获得**真实技术接触点**——「灵犀的确定性变换能力已封装为符合 OwO P3C 安全规范的签名插件」，而非口头联动。
- 成本：低。不破坏任一方安全模型。
- 限制：这块能力必须是灵犀 `assistant-core` 里**已有的确定性 Transformer / Diff**，不能是任何依赖模型或网络的能力。

### 方案 B：薄 owopkg 插件 + 外挂 daemon

- owopkg 内仅放一个**瘦客户端 exe**，被 PluginHost 拉起后通过 IPC 转发给沙箱外的灵犀 daemon（daemon 拥有网络 / UIA / 热键）。
- **违反 P3C 安全边界**：AppContainer 故意让回环端口都不可达，正是为防止插件逃逸到外部高权限进程；P3C 明确「不开放可伪造的外部调用入口」。
- 走这条路等于**修改 OwO 的沙箱策略**，开一个受信高权限插件通道。
- 成本：高。风险大，且削弱 OwO 已建立的安全叙事。不推荐在大创阶段做。

### 方案 C：平级 IPC 协作，谁也不做成谁的插件（架构最顺）

- OwO 作为真 TSF 输入法（负责打字底座），灵犀作为独立 Agent（负责 AI / 跨应用 / 桌宠），两者通过本地 IPC 平级协作。
- 最符合两者技术本质，无需破坏任何一方安全模型。
- 成本：中。需要定义一套两进程间的本地协作协议。

---

## 5. 推荐

**方案 A + 方案 C 组合**：

1. 主叙事走 C：OwO 打字底座 + 灵犀 AI Agent，平级协作。
2. 补一个 A 的「信物」：从灵犀抽一个纯本地确定性变换能力，打成合规 owopkg，证明灵犀能产出符合 OwO 安全规范的插件。

这样既尊重两个项目各自扎实的架构，又建立真实技术交集，答辩时故事完整、经得起追问「插件怎么调云端 / 怎么读 QQ」这类问题。

---

## 6. 若选方案 A，后续需要冻结的事项

（本文不含实现，仅列出下一步决策点）

- 选定要封装的确定性能力（建议：`assistant-core` 现有的 prefix / tidy / upper Transformer 或字符级 Diff 规整），确认其**不依赖 ModelBackend、不依赖网络**。
- 对齐 OwO `manifest.json` v1 字段与五项白名单权限（其中不含 network）。
- 明确 `.owopkg` 目录结构：根 `manifest.json` + `bin/<plugin>.exe`，路径为严格 UTF-8 相对路径。
- 签名：P3C 无未签名开发模式，需与 OwO 侧确认 P4/P5 的测试签名流程（真实发行证书在 OwO 侧 P5 才有）。
- 定义插件 IPC 服务（OWPH 协议、`.v1` 版本化服务名、≤256 KiB 负载、≤30 秒期限）下灵犀变换能力的输入 / 输出契约。

---

## 7. 结论

- 灵犀**整体**无法作为 owopkg 插件运行，能力冲突是架构级、非可修复的工程细节。
- 最务实的融合是「独立灵犀 + 一个合规的确定性变换 owopkg 插件」，并以 OwO 打字底座 + 灵犀 AI Agent 的平级协作作为主叙事。
- 若坚持让完整灵犀被 OwO 加载，唯一路径是修改 OwO 的 AppContainer 安全策略（方案 B），代价是牺牲 OwO 的核心安全卖点，不建议在当前阶段采用。
